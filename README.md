# bot-api-server

Go service for deploybot: Google OAuth sign-in and sessions, projects and members, join tokens and host credentials, the bot-agent WebSocket, metrics ingest into Postgres `deploybot`, live probes, and the REST API used by bot-console and bot-mcp-server.

- Design: `docs/design.md`
- Contracts (frozen, do not edit here): `docs/contracts/api-v1.md`, `docs/contracts/oauth-v1.md`, and `docs/contracts/agent-protocol-v1.md`.

## Run locally

Requires Go 1.27+ and a PostgreSQL 18 database with TimescaleDB. The server does not create tables on startup. `--migrate` does not create roles, schemas, or the TimescaleDB extension.

1. Copy `.env.example` to `.env` and replace every `CHANGE_ME` and `dummy-google-*` value. The example file is not a working configuration.
2. Create empty databases named `deploybot` and, for integration tests, `deploybot_test`. Do not create the extension yourself.
3. As a superuser, start a new session and run `migrations/roles.sql.example` as the first command in that session. Run it once connected to `deploybot`, and again connected to `deploybot_test`. Replace the `CHANGE_ME` passwords first. The script creates `deploybot_owner`, `deploybot_migrator`, and `deploybot_api`, installs `timescaledb`, and creates the `app` and `metrics` schemas. It is not applied by `--migrate`.
4. Apply the numbered migrations as `deploybot_migrator`:

   ```sh
   set -a
   source .env
   set +a
   go run ./cmd/bot-api-server --migrate
   ```

   `--migrate` reads `BOT_API_MIGRATE_DATABASE_URL`, runs `SET ROLE deploybot_owner`, and refuses to continue when `timescaledb` is missing. It is the only path that runs the numbered SQL files.
5. Start the API with `DATABASE_URL` pointing at `deploybot_api`:

   ```sh
   go run ./cmd/bot-api-server
   ```

   It listens on `BOT_API_LISTEN`. `GET /health` returns `{"status":"ok"}`.

`DEPLOYBOT_TEST_DATABASE_URL` is for integration tests only. Those tests refuse to run unless the connected database name is `deploybot_test`, and that database must already have had `roles.sql.example` applied. Leave the variable unset for `go test ./...`.

## Shared hosts

A host still belongs to one owning project. An owner admin can share it with another project at `metrics` or `deploy` (`PUT /v1/hosts/{id}/shares/{project_id}`). `GET /v1/projects/{id}/hosts` returns hosts that project owns and hosts shared with it. Owned hosts come first, then shared hosts, each ordered by name. The caller must be a member of the target project, and the owning project cannot be a share. Removing a share while that project still has services on the host returns 409 `conflict` unless `?reassign=owner` moves those services to the owner. Anyone who can see the host gets the full process list and may snapshot. Contract: `docs/contracts/api-v1.md` (v1.1.1). Behaviour: `docs/spec-shared-hosts.md`.

`migrations/0003_shared_hosts.sql` is applied by `--migrate`. It backfills `services.project_id` from the host, then sets the column `NOT NULL`, and grants `deploybot_api` select, insert, update, and delete on `app.host_shares`. `migrations/0003_shared_hosts.down.sql` is not applied by `--migrate`. Run that file by hand as `deploybot_owner`, and only before phase 2 (until then `services.project_id` can be rebuilt from the host). Then delete the applied row so a later `--migrate` will run 0003 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0003_shared_hosts.sql';
```

## Service names

A service keeps the discovered `name` the agent uses as its key. People set `display_name` with `PATCH /v1/services/{id}` and body `{"display_name": "<name>" | null}`. The name is trimmed, then it must be 1–64 printable characters. An empty string is `bad_request`. `null` clears it. The same name on one host, ignoring case, is `conflict`. The permission is the service edit capability from shared hosts: an owner admin, or a deploy-share admin renaming a service of its own project. The audit action is `service.rename`, including when the caller is denied. The agent stores the account that owns the listening socket in `owner_user` and never writes `display_name`. A later discovery batch updates `owner_user` and leaves the name.

`GET /v1/projects/{id}/services` lists every service on hosts that project owns, plus that project's own services on hosts shared with it at `deploy`. A metrics share adds no rows. The caller must be a member of the project; anyone else gets 404. `q` is a case-insensitive substring over the display name, discovered name, kind, host name, owner, and ports. `%`, `_`, and `\` match literally. `sort` is `name` (the display name, or the discovered name when the display name is null), `host`, `kind`, `status`, or `last_seen`. Name order is the byte order of the lowercased label, not the database locale. `dir` defaults to `asc`, and to `desc` for `last_seen`. The payload is `items`, `next_cursor`, `prev_cursor`, and `total`. The cursor is bound to `q`, `host_id`, `sort`, `dir`, and `view`. `GET /v1/hosts/{id}/services` orders by name in byte order (`COLLATE "C"`), like every other name sort, so Postgres and memstore agree. That list is otherwise unchanged apart from `display_name` and `owner_user` on each row.

`migrations/0004_service_names.sql` adds the two nullable columns and a unique index on `(host_id, lower(display_name))` where the name is not null. It does not change grants. `--migrate` does not apply `migrations/0004_service_names.down.sql`. That script drops the columns and the unique index. Names typed by people are lost. The project index from 0003 stays. After a hand run, delete the applied row before `--migrate` will apply 0004 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0004_service_names.sql';
```

`gone_at` is when a service was missing from its host's latest complete services report, or `null` when that report included it. Presence uses the stored name, so a matching catalog entry is kept under the entry name. A `services` frame is that host's full set when every element is valid, and an empty array is an empty set. In the same transaction, rows left out that are not already gone get `gone_at` set to the report time, and rows in the report have `gone_at` cleared. A row that is already gone keeps its time. Other hosts are not touched. `display_name`, health checks, and ids stay as they were. A mix of valid and invalid elements still stores the valid rows and clears their `gone_at`, and does not mark any other row gone. An all-invalid array, or a `services` value that is absent or JSON `null`, is not a report. `hello.services` follows the same rule when `services_complete` is absent or `true`. `services_complete: false` and JSON `null` write nothing and do not change presence. A non-bool fails the frame. `GET /v1/projects/{id}/services` takes `view`: `all` (the default), `deploybot` (`source` is `owned` or `declared`, gone or not, except a gone owned row whose catalog entry was deleted, which only `all` lists), or `deploybot_and_discovered` (those rows plus discovered rows that are still present). Any other value is `bad_request`. `q`, `host_id`, `sort`, `dir`, `limit`, `cursor`, and `total` apply inside the view. A cursor from one view is `bad_request` on another. `sort=status` lists present rows before gone rows, in both directions. `GET /v1/hosts/{id}/services` and `GET /v1/services/{id}` include `gone_at` and do not take `view`. Revoking a host sets `gone_at` to that revoke time on its rows that are still present, in the same transaction (`0012_revoked_host_rows.sql` backfills hosts revoked earlier), and `view=deploybot` and `view=deploybot_and_discovered` exclude rows whose host is revoked (`view=all` still returns them). A services report that places an item as `discovered` ends ownership of an existing `owned` row (`source` becomes `discovered`, `catalog_entry` becomes null, `project_id` becomes the host's project) and keeps the row id, `display_name`, and health checks; a `declared` row is not changed by a report.

`migrations/0008_service_gone.sql` adds nullable `services.gone_at`. On each host, a row whose `last_seen_at` is earlier than that host's newest `last_seen_at` is backfilled with `gone_at = last_seen_at`. Rows tied for that newest time stay null. Grants are unchanged. `--migrate` does not apply `migrations/0008_service_gone.down.sql`. That script drops the column. Presence is lost. After a hand run, delete the applied row before `--migrate` will apply 0008 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0008_service_gone.sql';
```

## Health checks over MCP

`PUT /v1/services/{id}/health-checks` still replaces the set immediately for a console session and pushes `config_update`. That replace locks the service row. A console session ignores `idempotency_key`. An `api_delegated` session must send one. After the same permission, share, and body checks, that call changes nothing and returns 202 `{"confirmation_id","plan","expires_at"}`. The plan names the service label (the display name, or the discovered name) and the host. The label and every HTTP path are Go-quoted (`strconv.Quote`). The host name is not quoted. A tcp check is `tcp <port>`. An http check is `http <port> <quoted path> every <interval> s`. A check with `enabled` false ends with ` (disabled)`. A tcp check that shares a port with an http check adds `(tcp <port> is redundant with http <port>)`. The set is still applied as given, including that tcp check. `POST /v1/confirmations/{confirmation_id}` reads `catalog_confirmations` first, then `app.service_confirmations`, then `app.catalog_write_confirmations`. Confirm compares the current set, marks the plan used, and replaces the checks in one transaction that locks `app.services` (`SELECT … FOR UPDATE`). A set that changed before that transaction commits is `conflict`, and the plan stays unused. Unknown, used, expired, and foreign ids are `not_found`. A matching confirm pushes `config_update` and returns `{"checks":[...]}`. Audit rows are `health_checks.confirmation_issued` (service, host, and check count) and `health_checks.replace` with `via` `mcp`. The audit `service` value is the raw label, not the quoted plan text.

`migrations/0011_service_confirmations.sql` creates that table. The row stores the normalized checks, because the confirm body does not send them again. `deploybot_api` may select, insert, and delete, and may update only `used_at`. `--migrate` does not apply `migrations/0011_service_confirmations.down.sql`. That script drops the table. Pending plans are lost. Nothing they named was applied yet. After a hand run, delete the applied row before `--migrate` will apply 0011 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0011_service_confirmations.sql';
```

## MCP OAuth

This process is the OAuth authorization server MCP clients use (`docs/contracts/oauth-v1.md`, api-v1 v1.4). A public client registers at `POST /oauth/register`. The person approves at the console. `POST /oauth/token` then issues an MCP access token (one hour) and a rotating refresh token (30 days). A second use of that code revokes the whole grant family, including later refreshes and delegated API tokens. `bot-mcp-server` exchanges a live MCP access token for a five-minute API token. Those exchanges are not counted against the token endpoint's per-IP limit; a missing or wrong client secret is. An MCP access token, an MCP refresh token, or a legacy `mcp` session presented to any `/v1/*` route is `401` with code `invalid_token`. The device flow (`POST /v1/auth/device/token`) issues an MCP access token for 30 days, in a grant family for the pseudo-client `deploybot-cli`. Looking up, approving, or denying a device code needs a console session.

An `api_delegated` session is refused, before membership is checked, on project create, rename, and delete; member add, role change, and remove; ownership transfer; join-token create and revoke; invite create and revoke; host credential revoke; host share put and delete; and service display-name patch. The response is 403 `forbidden`. Nothing is written. One audit row is `delegated.denied`, `decision` `denied`, `via` `mcp`, `error_code` `forbidden`, with detail `{"route":"<method pattern>"}` and null `project_id` and `host_id`. Snapshot, probe, catalog logs, status, and parse, sign-out, and `POST /v1/confirmations/{confirmation_id}` stay allowed. Routes that already plan a write or require a console session keep that behavior. A mutating `/v1` route added later is refused for this session until its route-table value says otherwise.

`BOT_API_PUBLIC_ORIGIN` is the issuer. A trailing slash is removed. `BOT_API_MCP_RESOURCE` is the audience clients must send: the MCP endpoint URL `<mcp origin>/mcp`, exactly as bot-mcp-server publishes it (e.g. `http://localhost:8091/mcp`); it is not trimmed. `BOT_API_CONSOLE_ORIGIN` is where `/oauth/authorize` sends the browser (`/oauth/consent?request=…`). When `BOT_API_MCP_RESOURCE` is set, `BOT_API_MCP_CLIENT_SECRET_FILE` is required before the process opens the database. The file must be a regular non-symlink file with mode `0600`. The first line is the plaintext secret for client id `bot-mcp-server` (a trailing CR is removed; a leading space is kept). That line must be at least 32 characters. A shorter line refuses to start, and the error does not include the secret. The database stores only the SHA-256 of that line. Leave `BOT_API_MCP_RESOURCE` empty to start without that client.

`migrations/0005_mcp_oauth.sql` adds the OAuth tables, the session columns (`audience`, `grant_id`, `client_id`, `code_id`, `rotated_at`), widens `sessions.kind`, inserts `deploybot-cli`, and expires every live `kind = 'mcp'` session. It grants `deploybot_api` select, insert, update, and delete on the four new tables. `--migrate` does not apply `migrations/0005_mcp_oauth.down.sql`. Run that file by hand as `deploybot_owner`. It deletes `mcp_access`, `mcp_refresh`, and `api_delegated` sessions, restores the old kind check, and drops the new columns and tables. Legacy `mcp` rows stay expired. Clients, grants, codes, and pending requests are lost. Then delete the applied row before `--migrate` will apply 0005 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0005_mcp_oauth.sql';
```

## Project invites

An owner or admin creates a link with `POST /v1/projects/{id}/invites`. The body is `role` (`admin` or `viewer`), optional `expires_in_sec` (3600–2592000, default 604800), and optional `max_uses` (1–50, default 1). The 201 response is the invite plus `token` and `url`. Those two fields are not returned again. `url` is `<BOT_API_CONSOLE_ORIGIN>/invite/<token>`. A trailing slash on the origin is removed. If the origin is empty, create returns 500 and does not store a token. `GET /v1/projects/{id}/invites` lists every invite for that project, newest first, including expired, revoked, and used-up rows. `DELETE /v1/projects/{id}/invites/{invite_id}` sets `revoked_at`. A second delete keeps the original timestamp. An invite that belongs to another project is `not_found`.

`POST /v1/invites/lookup` and `POST /v1/invites/accept` take `{"token":"..."}`. Both require a console session. Any other session kind is 401 `unauthorized`. Lookup and accept share a limit of 30 requests a minute per user and 60 a minute per source IP. Past either limit the response is 429 `rate_limited`. Lookup does not change the invite or the membership. An unknown, malformed, expired, revoked, or used-up token is `not_found`, and those responses are the same body. Accept runs in one transaction. Someone who is already a member gets their current role, and `uses` stays unchanged. Anyone else is added with the invite's role and `uses` increases by one. Concurrent accepts never go past `max_uses`.

The plaintext token is not stored, not logged, and not written into audit detail. Audit actions are `invite.create`, `invite.revoke`, and `invite.accept`. Deleting a project deletes its invites. Contract: `docs/contracts/api-v1.md` (v1.5). Behaviour: `docs/spec-project-invites.md`.

`migrations/0006_invites.sql` creates `app.invites`. `deploybot_api` may select and insert, and may update only `uses` and `revoked_at`. Soft-delete does not fire the foreign key, so the migration adds `app.invites_delete_for_project`, which runs as `deploybot_owner`. A real `DELETE` of the project still cascades. `--migrate` does not apply `migrations/0006_invites.down.sql`. Run that file by hand as `deploybot_owner`. It drops the helper and the table. Memberships already created by an accept stay. Invite links stop working. Then delete the applied row before `--migrate` will apply 0006 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0006_invites.sql';
```

## Project catalog

An owner adds a program with `POST /v1/projects/{id}/catalog`. The body is `name`, `kind` (`program`), `command`, `shell`, `dir`, `run_as`, and optional `env`, `port`, and `restart`. `name` is immutable. `POST /v1/projects/{id}/catalog/parse` previews the split (`exec`, `args`, `env`, `command_display`) and does not store a row. A program body that contains top-level `secret_env`, and any `kind` other than `program` or `image`, returns 501 `not_implemented`. An image body is `name`, `kind` (`image`), and `spec`. Program fields on an image, or a `spec` object on a program, are `bad_request`. Image entries, env sets, and registries are in the next section.

The server splits `command` on POSIX words. Quotes and backslash escapes are kept. With `shell=false`, a pipe, operator, redirect, `$`, backtick, glob, or a first word of `cd` is `bad_request`. Leading `KEY=value` words move into `env`. With `shell=true`, the line is not split: the program runs as `/bin/sh -c`, and that line is not scanned for environment names. Keys that start with `LD_` or `DYLD_`, and `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `IFS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, and `RUBYLIB`, are `bad_request` with the message `this variable changes what the program runs`. Hoisted `KEY=value` words are checked the same way. `spec_hash` is the SHA-256 of the canonical spec JSON. Replacing an entry with a new hash deletes every host approval of that entry. A replace that keeps the same hash leaves those approvals in place.

A new program entry grants admins run, stop, restart, and logs, and grants viewers logs. The owner of a program can always run, stop, restart, read logs, and read status. `PUT /v1/projects/{id}/catalog/{name}/permissions` replaces the grant list. A `user:` subject must be a current member and must not be the owner. At most 100 grants. `deploy` is a stored action for image entries only.

`POST .../run`, `/stop`, `/restart`, `/logs`, and `/status` take `host_id`. Run, stop, and restart also take `idempotency_key`. A non-member is `not_found` before the body is read. Invalid JSON and an invalid `host_id` are `bad_request` before the grant. A member who lacks the action is `forbidden` even when the key or `lines` are invalid. The key format and `lines` (1..1000) are checked after that grant. Status is allowed when they hold any action. The host must belong to the project, or be shared at `deploy` with an approval for the current `spec_hash`. A metrics share is `forbidden`. A deploy share that is not approved yet is `forbidden` with message `waiting for the host owner's approval`, and a pending approval is stored. That write does not clear a row already approved for the current `spec_hash`. The host's `programs` policy must be present, enabled, and list `run_as`. When `allow_shell` is false, shell mode and an exec whose base name is `sh`, `bash`, or `dash` are `forbidden` with message `shell is not allowed on this host`. An offline host is `unavailable`. Policy denials and an offline host are not stored as idempotency responses.

A console session runs the action. An `api_delegated` session, the token MCP uses on `/v1/*`, gets HTTP 202 for run, stop, and restart and does not touch the agent. The body is `confirmation_id`, `plan`, and `expires_at`. `POST /v1/confirmations/{confirmation_id}` takes `{"idempotency_key"}`. That key must equal the key from the original request. The same `api_delegated` bearer may confirm. An invalid key is `bad_request` and does not look up the id. A key that does not match is `conflict` with message `idempotency_key does not match the request that issued this confirmation`, and does not consume the token. The confirmation row stores only the SHA-256 of the id. The idempotency response keeps the 202 body, including `confirmation_id`, until confirm stores the outcome. The id is single use, lasts five minutes, and only the same user can redeem it. An unknown, used, expired, or foreign id is `not_found`. A lost grant, a policy failure, an offline host, or a spec change after the 202 does not consume the token. Logs and status do not ask for confirmation.

Run, stop, and restart insert the idempotency row before acting. The row is the user, the key, and the request hash, with no response yet. A second request with the same key while that response is empty is `conflict` with message `request in progress`, even when its hash differs. After the outcome, including a failed dispatch, the status and body are stored. The same request replays that body for 24 hours and does not act again. A finished row with a different hash is `conflict`. The request hash is the SHA-256 of compact JSON with keys `action`, `entry`, `host_id`, and `project_id`. It does not include `spec_hash`, so the same POST still replays after a replace. Confirm still compares the confirmation's `spec_hash`. A replay of a 202 does not create a second confirmation. Logs and status are not idempotent. The agent receives `program_start`, `program_stop`, `program_restart`, `program_status`, or `program_logs`. Strings in a payload `lines` array are redacted with the cmdline redactor before the HTTP body and before the idempotency write. `policy_denied` from the agent is `forbidden`.

`GET` and `POST /v1/hosts/{id}/catalog-approvals`, and `DELETE` of one entry, require an owner or admin of the host's owning project. A viewer of that project is `forbidden`. Anyone else is `not_found`. Each approval includes `exec`, `args`, and `env` with the command, directory, `run_as`, and shell, so the host owner sees everything that will run. Approving a hash that is not the entry's current `spec_hash` is `conflict` and does not write a row.

The agent hello may include `programs`. That object is stored on the host and returned as `Host.programs` (`null` when the agent sends none). A service report with `owner: {kind:"program", project, entry}` is stored as `source=owned` when that slug has that catalog entry. `catalog_entry` and the service name are the entry name. If the slug or the entry does not exist, the service stays `discovered` on the host's project. `systemd_unit` is used as that discovered name only when it matches `^[a-z0-9][a-z0-9._-]{0,62}$`. Otherwise the reported name is kept.

Audit rows are `catalog.create`, `catalog.update`, `catalog.delete`, `catalog.permissions`, `catalog.approve`, `catalog.approval_revoke`, `program.run`, `program.stop`, `program.restart`, and `program.confirmation_issued`. Delegated calls are `via=mcp`. Logs and status write no audit row. A denied run, stop, or restart records the host, `detail.entry` (the catalog name), and `Result` set to the envelope code (`forbidden` or `unavailable`). Env values and confirmation ids are not stored in the detail. Contract: `docs/contracts/api-v1.md` (v1.6 and the v1.6.1 amendments) and `docs/contracts/agent-protocol-v1.md` (v1.3 and the v1.3.1 amendments). This server enforces the v1.6.1 environment denylist. The helper socket and unit hardening in v1.3.1 belong to the agent. Behaviour: `docs/spec-project-catalog.md`.

`migrations/0007_catalog.sql` creates the catalog tables and adds `hosts.programs` and `services.catalog_entry`. `app.idempotency_keys.status_code` and `response` are nullable together: both null while a request is in progress, both set when the outcome is stored. `deploybot_api` may select, insert, and delete. It may update only the columns the server changes. `--migrate` does not apply `migrations/0007_catalog.down.sql`. Run that file by hand as `deploybot_owner`. It drops the new columns and tables. Running units are not stopped. Then delete the applied row before `--migrate` will apply 0007 again:

```sql
DELETE FROM app.schema_migrations WHERE name = '0007_catalog.sql';
```

## Catalog images

An owner creates an image entry with `POST /v1/projects/{id}/catalog` and body `name`, `kind` (`image`), and `spec`. `command_display` is the normalised image reference (`docker.io` and `library/` made explicit, and a missing tag becomes `:latest`). `spec_hash` is the SHA-256 of canonical JSON `{"env_keys","kind","spec"}`. `env_keys` hashes the sorted key names of each referenced env set. A value change does not change the hash. Adding or removing a key does, and that voids host approvals. Replacing the entry with a new hash does the same. Validation errors name the field and do not include the image, a command, an env value, a volume target, a user string, or a set name.

An `api_delegated` session validates an image create, replace, or delete and returns 202 `{confirmation_id, plan, expires_at}` without writing the entry. The plan lists the fields that will change, including inline env values, an entrypoint when set, and a restart policy when it is not the kind's default. It omits env-set values, secret_env values, and file contents. Caller-controlled text is Go-quoted unless it is a plain token. A program create, replace, or delete is `forbidden` with message `program entries are edited in the console`. That refusal, and a delegated permission change, host catalog approval, or catalog env route, is audited `denied` with `via` `mcp`. Delegated denials of the set routes use `env_set.list`, `env_set.get`, `env_set.replace`, or `env_set.delete`. Key put and key delete are refused before the handler and audited as `delegated.denied`. `POST /v1/confirmations/{id}` reads `app.catalog_write_confirmations` after the earlier confirmation tables, applies the stored spec on the console write path, and deletes the plan row. Applied `catalog.create`, `catalog.update`, and `catalog.delete` rows use `via` `mcp` whichever session confirms them. Issuing the plan writes `catalog.write_confirmation_issued`. Storing a plan deletes expired rows. Project delete deletes that project's rows. Permission changes, host catalog approvals, and catalog env routes stay console-only. `migrations/0013_catalog_write_confirmations.sql` creates the table. `deploybot_api` may select, insert, and delete, and may update only `used_at`. Both the user and project foreign keys use `ON DELETE CASCADE`. `--migrate` does not apply the down script.

A new image entry grants admins run, stop, restart, logs, and deploy, and grants viewers logs. The owner has those actions plus status. A program owner does not receive deploy. `POST .../deploy` on a program entry is `forbidden` for the owner. Image `logs` accepts `lines` from 1 to 2000 (default 200). Program logs stay 1 to 1000.

Deploy and rollback are synchronous: the 200 body is the outcome. A remove that times out is the request-level envelope error `timeout` (HTTP 504), audits outcome `timeout`, and is never reported as `missing`. A deploy or rollback that times out with no agent payload is HTTP 200 with outcome `timeout` and `status.state` `unknown`. `container`, `exit_code`, `started_at`, `finished_at`, and `digest` are null, `restart_count` is 0, and `ports` is empty. An agent result of `unknown` is rejected. The task `timeout_sec` is `300 + healthy_after_sec + 60` for a service deploy and for every rollback. When the spec has `healthcheck`, both use `300 + max(healthy_after_sec, start_period_sec + interval_sec × (retries + 1)) + 60`. A job deploy is `300 + timeout_sec + 60`. Remove, run, stop, restart, status, and logs are 60. `expires_at` is that many seconds ahead when the timeout is above 60, and 60 seconds ahead otherwise. The handler detaches deploy, rollback, and remove from the HTTP request with `context.WithoutCancel`, then bounds the hub wait by the task timeout. The history write, the in-flight release, and the idempotency finish use a fresh context with a five-second timeout and retry once, including when the task context has already expired. The HTTP server does not set `WriteTimeout` (`ReadHeaderTimeout` 10s, `ReadTimeout` 30s, `IdleTimeout` 120s), so that wait is not cut short by the server write deadline. One deploy, rollback, or remove may be in flight per host and entry. A second is `conflict`. The database enforces that with a partial unique index on `app.image_deploys`. Each in-flight row stores `in_flight_until` (the task timeout plus 120 seconds). The next deploy, rollback, or remove for that host and entry marks an expired row outcome `timeout`, clears it in the same transaction, and continues. A row that has not reached that deadline is still `conflict`. Rollback accepts one of the last three distinct digests whose outcome was `succeeded` or `unchanged` for that entry and host. Another digest is `bad_request` with message `invalid digest` and is not echoed.

The host must have reported `programs.images` and `programs.docker`. Otherwise the action is `bad_request` with message `this host does not run containers`. An entry with a non-empty `files` list also requires `programs.files`. Otherwise deploy and rollback are `bad_request` with message `this host's agent does not support files`, before confirmation and before any task. Entries with no files are unchanged. The secrets key is checked before the idempotency claim and before a confirmation is issued, so a missing key is not stored for 24 hours. It is required when the entry names an env set, uses `secret_env`, a `files` row still names a secret file, or the image's registry host has a stored registry. The response is 503 `unavailable` with message `secrets key not configured`. A public image with no matching registry deploys without the key. Run, stop, restart, status, and remove do not need it. Logs need it only when the resolved env includes a secret key or a files row still names a secret file. A missing key is then 503 `unavailable` with message `secrets key not configured`: no task is sent and no lines are returned. A plain winning value, a plain file, and a registry credential do not trigger that refusal. Inline `env` clears a secret flag. Idempotency matches programs: the claim is stored before a delegated session receives its 202. A deploy hash also includes `force`. A rollback hash includes `digest`. The plan text is `will deploy <entry> (<image or digest>) on <host>`, `will remove <entry> on <host>`, or `will <action> <entry> on <host>`. It contains no env values or tokens.

A Docker health sample (`protocol` `docker`, `result` `success` or `unhealthy`, `http_status` and `latency_ms` null, no `check_id` or `port`) is stored only when that host's hello set `programs.docker_health`. Otherwise the batch is rejected as an invalid sample and the socket stays up. `config.docker_health` is `true` on `hello_ok` and `config_update` only for such a host, and is omitted otherwise. Service health uses a `docker` row at most 2 minutes old (`success` is `up`, `unhealthy` is `down`) ahead of the latest non-docker row. `health.source` is `docker`, `check`, or null, and `latency_ms` is null for Docker. `GET /v1/services/{id}/health` includes those rows with `check_id`, `port`, `http_status`, and `latency_ms` null. An optional image `healthcheck` (`test` of 1–32 strings, each 1–1024 bytes and no NUL, plus `interval_sec` 5–300, `timeout_sec` 1–60 and less than the interval, `retries` 1–10, `start_period_sec` 0–600) is stored with omitted numbers filled as 30, 5, 3, and 0, and is part of `spec_hash`. A job is `bad_request` with message `healthcheck applies to services`. Other errors name the field and do not echo `test`. Deploy and rollback of an entry that has one require `programs.healthcheck`, or the response is `bad_request` with message `this host's agent does not support healthcheck`, before confirmation and before any task. `programs` is jsonb, so these booleans need no migration.

Env sets and registries require an owner or admin (`CapMembers`) and a console session. A viewer is `forbidden`. A delegated or MCP token is `forbidden` before any decrypt. A delegated env-set refusal is audited `denied` with `via` `mcp`. A non-member is `not_found`. `GET` and `PUT /v1/projects/{id}/env-sets/{set}` and `DELETE` of that set, `PUT` and `DELETE .../keys/{key}`, and `GET /v1/projects/{id}/registries` plus `PUT` and `DELETE /v1/projects/{id}/registries/{host}` are the routes. `GET` of an env set returns a secret value as JSON `null` and `preview` of that secret, and returns a plain value with `preview` null. `PUT` replaces the set from a dotenv body of at most 256 KiB. A key that already exists keeps its visibility. A key new to the set is stored as secret unless the body sets `new_keys_secret` to false. A key left out of the body is removed. The grammar is UTF-8, optional `export `, `#` comments, and one pair of matching quotes removed, with no escape processing and no interpolation. `$` and `\` are stored as written. NUL is refused, a value does not span lines, and a value is at most 4096 bytes. Inline ImageSpec `env` keeps the v1.6 item 8 rules. A duplicate or a malformed line is `bad_request` naming `line N` and the key when one was parsed, never the value. `DELETE` of a set that an entry still references is `conflict`. A registry `GET` returns `host` and `username` only. `PUT` takes `username` (1–255) and `token` (1–4096) with no CR, LF, or NUL. The host is a lowercase hostname with an optional port. An invalid host, username, or token is `bad_request` and the message does not echo the value.

`PUT` and `DELETE /v1/projects/{id}/env-sets/{set}/keys/{key}` edit one key. The put body is `{"value","is_secret"?}`. `is_secret` applies only to a new key and defaults to true; an existing key keeps its flag, and a different flag is `bad_request` with message `secret flag is fixed; delete and re-add the key`. The put creates the set when it is missing and returns that one key. A secret key has `value` null and `preview`: the first four runes plus `…` when the value has at least 16 runes, otherwise `••••`. A plain key has `preview` null. Delete of an unknown key is `not_found` and leaves the set in place when it was the last key. Both routes are console-only. An `api_delegated` call is `delegated.denied`. Adding or deleting a key voids host approvals of entries that use the set; changing only the value does not. `PATCH` of a key is not a route. A dotenv put may set `new_keys_secret` (default true) for keys that are new to the set. `PUT` of a catalog entry is owner or admin, on the console and on a delegated plan and its confirm. The response `my_actions` follows the caller's role, so an admin sees the stored admin grants plus `status`. Create, delete, and permissions stay owner-only.

`BOT_SECRETS_KEY_FILE` is optional. Leave it unset and the process starts; env-set and registry writes, and a deploy or rollback that needs the key, return `secrets key not configured`. When it is set, the file must be a regular non-symlink file with mode `0600`. The open uses `O_NOFOLLOW`. The first line is standard base64 of exactly 32 bytes. A file that fails those checks refuses startup. Errors name the variable and do not include the path's contents or the key. Values and tokens are AES-256-GCM. Each secret write stores a fresh 12-byte nonce, the ciphertext, and `key_version` 1. A plain env value is stored as text. The additional data is `project_id|set|key`, `project_id|registry|host`, or `project_id|file|name`. A decrypt failure on deploy or rollback does not send the task. The HTTP body is `internal error`. The log line is `decrypt failed`, with no value, nonce, or ciphertext. An `image_deploy` or `image_rollback` frame carries the stored ImageSpec (inline `env` as written, `env_sets` and `secret_env` as references) the resolved env map once, as the top-level `env`, and, when `spec.files` is non-empty, a top-level `files` array in that order. An empty list is omitted from the frame and from `spec`, because a wave 2a agent rejects the key. `secret_keys` is included only when the host's stored `programs.files` is true, and then always, including an empty list. The names are sorted. A key is listed when its resolved value comes from an env-set key with `is_secret: true` (through `env_sets` or `secret_env`) and inline `env` did not override it. A host without `files` does not receive the key. `registry_auth` is the one credential whose host equals the normalised image registry, or `null`. Each secret value appears once. A frame over the agent limit is `bad_request` with message `the resolved environment and files are too large for one task`: nothing is written, the socket stays up, the in-flight row is released, and the attempt is not audited as a deploy. Every websocket write is capped at 10 seconds even when the task timeout is longer. Audit rows, history rows, plans, and error text do not contain those values. Lines, error strings, the idempotency body, and every string field of `ImageStatus` and `ImageDeploy` are redacted by replacing env-set secret values with `preview(v)` and the registry token and secret-file pieces with `[REDACTED]` first (raw, base64, and JSON-escaped, at least 6 bytes), then the keyword rule. An error string is redacted in place. The audit reason for that failure stays the fixed phrase for its code. Inline `env` values and plain env-set values are not redacted. The API uses that secret-only set even when it omits `secret_keys`. A secret-file piece is the whole content when it is 6–4096 bytes, a trimmed line of 16–4096 bytes, or, when the content is JSON, a string value of 16–4096 bytes or a trimmed line inside that value. Each piece uses the same raw, base64, and JSON-escaped forms. Secret files under 6 bytes are not redacted from logs. A secret whose single line is longer than 4096 bytes is not exact-matched (the per-piece bound; helper log lines are cut at 2048 bytes). Logs, status, run, stop, restart, remove, deploy, and rollback apply that replacement to free-text `lines`, to error messages, and to every string field of `ImageStatus` and `ImageDeploy` (`container`, `state`, `started_at`, `finished_at`, `digest`, and on a deploy record `spec_hash`, `outcome`, and `via`). `exit_code` is not text. Status text is checked as printable ASCII before that replacement, so a preview is not rejected. A stored idempotency body is that same response. The history row keeps the digest that was stored. The history GET redacts a copy of each row with the same forms, and leaves the stored digest for rollback. Their task frame stays `project` and `entry`, and logs adds `lines` as a count. The env values and the matching registry token are decrypted only to build the redaction set. A missing key on status, run, stop, restart, and remove keeps the keyword rule, returns the agent text, and logs no error. Logs do the same when the entry has no secret env key and no secret file. When it has either, a missing key refuses the call as above and returns no lines. A decrypt failure on these actions still returns the agent text, redacts every secret value and secret-file piece that opened, and writes one `decrypt failed` line with no value. An env or registry decrypt failure does not drop file pieces that opened. An agent result outside the outcome, state, length, or digest rules is outcome `failed` with the fixed message `invalid agent result` on deploy and rollback. An env-set replace audit lists key names. A deploy history row does not list env. The API does not store the task frame.

`hello.programs` may include `images`, `docker`, and `files` (each default false). A discovered service with `kind:"container"` stores `container_name` and `image_digest` on the Service object. `container_name` must be a printable token of at most 128 bytes. An empty, oversized, or non-printable name drops that service. A missing name is kept. A name that passes is stored after the cmdline redactor, so an assignment such as `password=…` is not returned to a viewer. Discovery does not decrypt env sets to strip exact values. `owner: {kind:"image", project, entry}` is `source=owned` when that slug has an image entry of that name. The service name and `catalog_entry` are the entry name. A miss keeps the reported container name. An image owner does not attach to a program entry, and a program owner does not attach to an image entry.

Audit actions added for this surface are `catalog.deploy`, `catalog.rollback`, `catalog.remove`, `env_set.replace`, `env_set.key_put`, `env_set.key_delete`, `env_set.delete`, `registry.put`, `registry.delete`, `file.put`, and `file.delete`. Detail is names, hosts, digests, outcomes, `via`, and key names. Image run, stop, restart, logs, and status write no audit row. A denied deploy, rollback, or remove records the fixed phrase when the agent message contained a secret form, and otherwise that message, plus the envelope code. The HTTP `msg` is the redacted text. After the agent answers, `result` stays the outcome and `error_code` is that outcome unless it is `succeeded` or `unchanged`, which leave `error_code` null. Issuing a confirmation still uses `program.confirmation_issued`. Contract: `docs/contracts/api-v1.md` (v1.8 catalog images) and `docs/contracts/agent-protocol-v1.md` (v1.4 images). ## Project files

A project stores at most 64 files. A name matches `^[a-z0-9][a-z0-9._-]{0,63}$`. Content is UTF-8, 1–65536 bytes, and contains no NUL. `GET /v1/projects/{id}/files`, `GET`, `PUT`, and `DELETE /v1/projects/{id}/files/{name}` require an owner or admin and a console session. A viewer is `forbidden`. A delegated token is `forbidden` before any decrypt. An `mcp_access` or `mcp_refresh` token is `invalid_token` on every `/v1` route, including these, before the handler runs. A non-member is `not_found`. `PUT` takes `{"content","secret"}`. An omitted or JSON `null` `secret` means `true`. The response is metadata and never the content. `sha256` is stored for every file and returned only for a plain file. `GET` of one secret file is `forbidden`. `GET` of one plain file returns its content. The list is sorted by name and never includes content. A new name past 64 files is `bad_request` with message `too many files`. Replacing an existing name at that limit is allowed. `DELETE` takes the same project-row lock as `PUT` before it checks references. `DELETE` of a file that an image entry still names is `conflict` with message `referenced by` and the entry names, and writes one `file.delete` audit row (`name`, `outcome` `conflict`). An unknown name is `not_found`. Errors do not echo content. A body that is not valid UTF-8 is `invalid json`, because the JSON decoder would otherwise replace those bytes.

Secret content is AES-256-GCM with a fresh 12-byte nonce, `key_version` 1, and additional data `project_id|file|name`. Without the secrets key, `PUT` of a secret file, a deploy or rollback whose `files` still name a secret file, and logs for that entry, return `unavailable` with message `secrets key not configured`. Logs return no lines and send no task. Plain files do not need the key. A decrypt failure does not send the task. The HTTP body is `internal error` and the log line is `decrypt failed`.

An image spec's `files` is at most 16 `{file, target}` rows. It defaults to `[]` and is always present in a stored spec and in a catalog GET. `spec_hash` covers the names and targets, not the content, and omits an empty list, so an entry without files keeps the wave 2a hash and a content change does not void an approval. An unknown file is `bad_request` `unknown file`. A bad target, or the same `file` name twice, is `bad_request` `invalid files`. A file target that overlaps a volume target is the same error: both paths are cleaned first, a volume that cleans to `/` overlaps every file, and an exact match or a `/` boundary either way overlaps. An entry with no files still accepts a volume of `/`, a trailing slash, or an empty segment. Neither message includes a value. A file deleted after the entry was saved makes deploy and rollback `bad_request` with message `file <name> no longer exists`, and no task is sent. The host-support check above runs again when a confirmation is posted, and a denial does not consume the token. The `image_deploy` and `image_rollback` frame carries a top-level `files` array in `spec.files` order when that list is non-empty. Each row is `name`, `target`, `content`, and `secret`. An empty list is omitted at both levels. That array is the only place secret content leaves the API. Task records, logs, history, plans, and audit keep names and targets. `image_logs` carries no file content. Its response, and deploy and rollback result lines, redact secret-file pieces as described above. An env or registry decrypt failure does not drop pieces from files that opened. A missing or undecryptable sibling is skipped while building that set. Deploy and rollback still return `bad_request` when a named file is gone. Plain file content is not redacted. Secret files under 6 bytes are not redacted from logs. A secret whose single line is longer than 4096 bytes is not exact-matched (the per-piece bound; helper log lines are cut at 2048 bytes). The plan text does not change. Audit is `file.put` (`name`, `is_secret`, `size`) and `file.delete` (`name`, `outcome`). A completed delete has `outcome` `deleted`. A delete refused because an entry still names the file has `outcome` `conflict`. Neither row contains content or `sha256`. `hello.programs.files` absent means false.

The 64-file limit is enforced by the server. `--migrate` does not apply `migrations/0010_project_files.down.sql`.
