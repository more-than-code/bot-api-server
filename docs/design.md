# bot-api-server: per-repo design

**Date:** 2026-10-13. **Status:** Approved design (D1–D31), wave 1 = phase 1. D34 (2026-10-14) amends umbrella D21. Service names and `GET /v1/projects/{id}/services` (2026-10-14) follow `docs/spec-project-services.md`. The MCP OAuth authorization server (2026-10-14) follows `docs/spec-mcp-oauth.md` and `docs/contracts/oauth-v1.md`. Project invite links (2026-10-15) follow `docs/spec-project-invites.md` and api-v1 v1.5. Project catalog programs (2026-10-15) follow `docs/spec-project-catalog.md` wave 1, api-v1 v1.6, and the v1.6.1 amendments. Catalog images, env sets, and registries (2026-10-15) follow `docs/spec-catalog-images.md` rev 3, api-v1 v1.8, and agent-protocol v1.4. Project files and `files` on image entries (2026-10-16) follow `docs/spec-catalog-files.md` rev 1, api-v1 v1.9, and agent-protocol v1.5. Health-check replacement from an `api_delegated` session (api-v1 v1.10, 2026-10-18) returns a confirmation plan and applies the set only on `POST /v1/confirmations/{id}`. The v1.3.1 environment denylist is enforced here. The helper socket and unit hardening in agent-protocol v1.3.1 are not implemented in this server.
Cross-repo design: umbrella `docs/design-bot-agent-deploy.md` §2 (permissions), §3 (auth), §6 (server, app schema, Postgres roles and metrics). Contracts: `docs/contracts/`.

| `BOT_SECRETS_KEY_FILE` | optional; mode `0600` regular file, not a symlink, opened with `O_NOFOLLOW`; first line is standard base64 of exactly 32 bytes (AES-256-GCM, `key_version` 1). TLS terminates at the reverse proxy in production; dev listens on the tailnet.

## Notes

- One process. In-flight tasks, OAuth states, and live agent connections are in memory.
- Metrics tables use `timestamptz`. Raw retention is 7 days; hourly continuous aggregates are kept 1 year (add the policies in migrations; they need TimescaleDB enabled by Joe).

## D34 Shared hosts

Amends umbrella D21 ("a host belongs to exactly one project"). The host still has one owning project (`hosts.project_id`). `app.host_shares` grants another project `metrics` or `deploy` access. A row whose project is the owning project is rejected by a `BEFORE` trigger and by the store. `services.project_id` records which project a service belongs to. The agent still enrolls with no protocol change; a discovered service is inserted on the host's owning project, and rediscovery does not move `project_id`.

Permission checks for host and service routes use `authz.HostRelation` and `authz.AuthorizeHost` (spec §4). A user who is in both the owning project and a share is an owner; that clears the share list. A user in several shares keeps every share. Host view, status, and metrics are allowed when any share allows them. A service check uses only the share whose project is that service's project. `GET /v1/hosts/{id}` `share_level` is the highest of those shares (`deploy` over `metrics`). `GET /v1/projects/{id}/hosts` is different: the label is relative to that project, so the same user listing the sharing project still sees `relation: "shared"`. Owned rows come first, then shared rows, each by name in byte order (`COLLATE "C"`). The host-list cursor is `(rel_rank, name, id)`. The next page compares those values and does not look the cursor host up. A cursor in the previous `(time, id)` shape is rejected. Deploy shares still see only that project's services; anyone who can see the host gets the full process list and may snapshot (v1.1.1). A caller in two deploy shares sees both projects. Metrics shares can read the host and its charts.

Deleting a sharing project drops its shares and moves its services on other hosts back to those hosts' owners, in the same transaction. Deleting the owning project still revokes host credentials, and its shares go too. Deleting a host row drops `host_shares` by `ON DELETE CASCADE`.

`migrations/0003_shared_hosts.sql` is applied by `--migrate` (as `deploybot_owner`). It backfills `services.project_id`, then sets `NOT NULL`, and grants `deploybot_api` select, insert, update, and delete on `app.host_shares`. `--migrate` ignores `*.down.sql`. `migrations/0003_shared_hosts.down.sql` is a hand-run rollback for before phase 2: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0003_shared_hosts.sql'` before `--migrate` will apply 0003 again.

## Service names

`services.display_name` is the name a person types. `services.owner_user` is the account that owns the listening socket, copied from the agent's `Discovered.user`. Both are nullable. Rediscovery updates `owner_user` and the other discovered columns; it does not write `display_name`. A value that is empty, not printable, or longer than 64 bytes is stored as null and does not drop the service.

`PATCH /v1/services/{id}` sets or clears `display_name`. The body is that one field. The handler trims it and requires 1–64 printable characters. The edit permission is the shared-hosts service write capability: owner admin+, or a deploy-share admin for a service whose project is that share. A case-insensitive duplicate on the same host is `conflict`, from the partial unique index. The audit action is `service.rename` with detail `from` and `to`, on success and on denial.

`GET /v1/projects/{id}/services` requires project membership (`CapRead`). Rows are every service on hosts the project owns, plus services whose `project_id` is that project on hosts shared at `deploy`. A metrics share contributes nothing, including services that belong to the metrics project. Each row is the Service object plus `host_name`, `host_status` (the same rules as `Host.status`), and `project_name`. Search, sort, `total`, and paging run in SQL: one count and one page. `q` is bound with `LIKE` wildcards escaped. Sort and direction are an allowlist. Names sort by byte order of the lowercased label (`COLLATE "C"`), not locale. Host and kind use that same collation on the stored text. Ties break by `id` ascending. Nulls sort last in both directions. The cursor is opaque base64url JSON `{o, h}`: an offset and a short hash of `q`, `host_id`, `sort`, `dir`, and `view`. The first page has `prev_cursor` null. `GET /v1/hosts/{id}/services` orders by name in byte order (`COLLATE "C"`), like every other name sort, so Postgres and memstore agree. That list is otherwise unchanged apart from the two new Service fields.

`migrations/0004_service_names.sql` adds the columns and `services_host_display_name_uidx`. `services_project_idx` already exists from 0003; 0004 creates it only if it is missing, and the down script does not drop it. `--migrate` does not apply `migrations/0004_service_names.down.sql`. Running that file by hand drops the two columns and the unique index. Names typed by people are lost. Then `DELETE FROM app.schema_migrations WHERE name = '0004_service_names.sql'` before `--migrate` will apply 0004 again. Grants are unchanged.

`services.gone_at` is when a service was missing from its host's latest complete services report. Null means that report included it. Presence uses the stored name after placement, so a matching catalog entry is stored under the entry name, not the name the agent sent. The upsert and the presence update run in one transaction when the report is complete: unreported rows that are not already gone get `gone_at` set to the report time, and reported rows have `gone_at` cleared. An already-gone row keeps its time. Other hosts are not modified. A `services` frame is that full set when every element is valid. An empty array is an empty set. A mix of valid and invalid elements still upserts the valid rows and clears their `gone_at`, and does not mark any other row gone. An array whose every element is invalid, or a payload that is absent, blank, or JSON `null`, is not a report. `hello.services` follows the same rule when `services_complete` is absent or `true`. `services_complete: false` and JSON `null` write nothing. A non-bool fails the frame. `GET /v1/projects/{id}/services` accepts `view` `all` (default), `deploybot` (`owned` and `declared`), or `deploybot_and_discovered` (those plus discovered rows still present). Anything else is `bad_request`. Search, sort, paging, and `total` stay inside the view, and the cursor hash includes the view. `sort=status` keeps gone rows after present rows in both directions. Host and service reads include `gone_at` and do not filter by view. `migrations/0008_service_gone.sql` adds the nullable column and backfills each host from its own newest `last_seen_at`. `--migrate` does not apply `migrations/0008_service_gone.down.sql`. Running that file by hand drops the column. Then `DELETE FROM app.schema_migrations WHERE name = '0008_service_gone.sql'` before `--migrate` will apply 0008 again. Grants are unchanged. Revoking a host sets `gone_at` to that revoke time on its rows that are still present, in the same transaction (`0012_revoked_host_rows.sql` backfills hosts revoked earlier), and `view=deploybot` and `view=deploybot_and_discovered` exclude rows whose host is revoked (`view=all` still returns them). A services report that places an item as `discovered` ends ownership of an existing `owned` row (`source` becomes `discovered`, `catalog_entry` becomes null, `project_id` becomes the host's project) and keeps the row id, `display_name`, and health checks; a `declared` row is not changed by a report.

## MCP OAuth authorization server

Public clients register themselves. The browser consent routes, the device-code lookup and approve/deny routes, and `GET`/`DELETE /v1/me/grants` require a console session. Any other session kind on those routes is 401. `POST /oauth/token` accepts `authorization_code`, `refresh_token`, and the token-exchange grant. Only `bot-mcp-server`, authenticated with HTTP Basic and the secret from `BOT_API_MCP_CLIENT_SECRET_FILE`, may call token exchange. A request that passes that Basic authentication is not counted against the token endpoint's 60-per-minute per-IP limit. A missing or wrong secret is counted. That client is inserted at process start from the SHA-256 of the file's first line. It is not created by dynamic registration. Codes, refresh tokens, access tokens, and the client secret are stored as SHA-256. Comparison is constant-time. Identifiers and codes are at least 128 bits from `crypto/rand`; tokens are 256 bits. A second redemption of an authorization code revokes every session in that grant family, including tokens from later refreshes and `api_delegated` sessions. Presenting an already-rotated refresh token does the same.

An `mcp_access`, `mcp_refresh`, or legacy `mcp` session on any `/v1/*` route is rejected with `invalid_token` before the handler runs. An `api_delegated` token acts as its user. Audit rows it causes use `via = 'mcp'`. The column check is `allowed|denied`, so an allow or deny decision is stored as `allowed` or `denied`.

`migrations/0005_mcp_oauth.sql` is applied by `--migrate` as `deploybot_owner`. It adds `app.oauth_clients`, `app.oauth_grants`, `app.oauth_requests`, and `app.oauth_codes`, the session columns `audience`, `grant_id`, `client_id`, `code_id`, and `rotated_at`, and widens `sessions_kind_chk` to `console|mcp|mcp_access|mcp_refresh|api_delegated`. `kind = 'mcp'` stays legal so the cut-over can expire those rows in place: `UPDATE app.sessions SET expires_at = now() WHERE kind = 'mcp' AND expires_at > now()`. `deploybot-cli` is inserted for the device flow. `deploybot_api` receives select, insert, update, and delete on the four new tables. `--migrate` ignores `*.down.sql`. `migrations/0005_mcp_oauth.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0005_mcp_oauth.sql'` before `--migrate` will apply 0005 again. The down script deletes sessions whose kind is not `console` or `mcp`, restores the 0001 kind check, and drops the new columns and tables. Legacy `mcp` rows stay expired. Clients, grants, codes, and pending requests are lost.

## Project invite links

An invite is a bearer token for project membership, separate from host join tokens. The plaintext is 256 bits, 43-character unpadded base64url, shown once in `POST /v1/projects/{id}/invites` as `token` and as `url`. The store keeps only `secret.Hash` of that string. List, revoke, lookup, and accept never return it. Logs and audit detail do not contain it or its hash.

`url` is `<BOT_API_CONSOLE_ORIGIN>/invite/<token>`. The handler trims trailing slashes on the origin, the same way the OAuth consent redirect does. An empty origin fails the create with 500 before `secret.NewToken` runs. Admin routes use `authz.CapMembers` (owner or admin). A viewer is `forbidden`. A non-member is `not_found`. Lookup and accept require a `console` session; another kind is 401 `unauthorized`. Those two routes call `authz.Authorize` with `CapSession`, then `auth.AllowInvite`: 30 per minute per user and 60 per minute per source IP, one window, and a rejected call is not counted. The HTTP body is the v1 envelope `rate_limited` (429). The OAuth token endpoint still uses its own `{"error":"rate_limited"}` body.

Lookup is a plain select. It returns the invite's role and `already_member`, and it does not write. Accept locks the invite row by `UPDATE app.invites SET uses = uses WHERE token_hash = $1`, which `deploybot_api` is allowed to do. `SELECT … FOR UPDATE` would also need `UPDATE` on every returned column, and this role only has `UPDATE` on `uses` and `revoked_at`. The lock update is rolled back unless a new membership row was inserted and `uses` was incremented. An existing member gets their current role back; `uses` and the role stay as they were. A new member is inserted with the invite's role and `added_by` set to the invite's `created_by`. `uses` is incremented only while `uses < max_uses`. The memstore holds its mutex for the whole accept, so the cap is the same there. Unknown, malformed, expired, revoked, and used-up tokens hash to a lookup and return one `not_found` body. A used-up invite is `not_found` even for someone who is already a member.

Audit rows are `invite.create` (invite id, role, max_uses, expires_at), `invite.revoke` (invite id), and `invite.accept` (invite id, user id), including an accept that finds an existing member. Lookup writes no audit row.

`migrations/0006_invites.sql` is applied by `--migrate` as `deploybot_owner`. `app.invites.project_id` references `app.projects` `ON DELETE CASCADE`. `token_hash` is unique and 32 bytes. `role` is `admin` or `viewer`. `max_uses` is 1–50. `uses` is 0–`max_uses`. Default privileges would grant `deploybot_api` full CRUD, so the migration revokes that and grants select, insert, and update of `uses` and `revoked_at` only. Soft-delete does not fire the foreign key. `DeleteProject` calls `app.invites_delete_for_project`, a `SECURITY DEFINER` function with `search_path = pg_catalog, app`, executable by `deploybot_api` and not by `PUBLIC`. The memstore deletes that project's invite rows under the same mutex. `--migrate` ignores `*.down.sql`. `migrations/0006_invites.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0006_invites.sql'` before `--migrate` will apply 0006 again. The down script drops the function and the table. Memberships already created by an accept stay. Invite links stop working.

## Project catalog (programs)

Wave 1 stores program entries. A program body that contains top-level `secret_env`, and any `kind` other than `program` or `image`, is refused with `not_implemented` (HTTP 501) before unknown-field checks. Image entries use `spec` and are described under Catalog images. The `docker run` parser is not implemented. After migration 0009, `catalog_entries.kind` allows `program` and `image`.

An owner creates and replaces entries. The server splits `command` with POSIX word rules (quotes and backslash escapes only). `shell=false` refuses pipes, operators, redirects, expansion, globs, and a first word `cd`. Leading `KEY=value` words are hoisted into `env`. Keys that start with `LD_` or `DYLD_`, and `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `IFS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, and `RUBYLIB`, are refused with `bad_request` and the message `this variable changes what the program runs`, including hoisted words. A `shell=true` line is not scanned for those names. `shell=true` stores `exec=/bin/sh` and `args=["-c", line]`. `spec_hash` is the lowercase hex SHA-256 of the canonical JSON `{"kind":"program","spec":{...}}` with keys sorted and no whitespace. `exec` is part of that document. `command_display` is the argv re-joined with POSIX quoting, or the raw line in shell mode.

Default grants are `role:admin` → run, stop, restart, logs, and `role:viewer` → logs. The owner always has run, stop, restart, logs, and status, and cannot be a subject. `status` is not stored; it is allowed when the caller holds any stored action. `my_actions` is that list in the order run, stop, restart, logs, status. List returns an entry only when `my_actions` is non-empty. A member with no grant who fetches one entry gets `forbidden`. A non-member gets `not_found`.

Run, stop, restart, logs, and status use one ordered chain. Membership of project `{id}` is `not_found` before the body is read. Invalid JSON and an invalid `host_id` are `bad_request`. A missing grant is then `forbidden`, including when `idempotency_key` or `lines` would also be invalid. The key format and `lines` (1..1000) are checked after the grant. The host must be owned by that project, or shared at `deploy` with an approval whose `spec_hash` is the entry's current hash and whose status is `approved`. A metrics share is `forbidden`. A deploy share without that approval is `forbidden` with the message `waiting for the host owner's approval`, and the server upserts a pending approval requested by the caller. That upsert updates a row only when it is still pending or its `spec_hash` differs. It does not clear an approved row for the current hash. The approval object includes `exec`, `args`, and `env`. Approving a hash other than the entry's current `spec_hash` returns `conflict` and writes nothing. Policy is next: null `programs`, `enabled=false`, `run_as` not listed, or shell when `allow_shell` is false. Shell also includes an exec whose base name is `sh`, `bash`, or `dash`. Each of those is `forbidden` with its own reason. The host is then required to be online. Policy denials and an offline host are not stored as idempotency responses. Run, stop, and restart then insert the idempotency row (user, key, request hash, null status, null response) before any agent call or confirmation. A second request with the same key while the response is null is `conflict` with message `request in progress`, even when the hash differs. After the outcome, including a failed dispatch, the status and body are filled in. The same request replays that body for 24 hours and does not act again. A finished row with a different hash is `conflict`. The request hash is the SHA-256 of compact JSON with keys `action`, `entry`, `host_id`, and `project_id`. It does not include `spec_hash`. An `api_delegated` session gets HTTP 202 for run, stop, and restart and does not call the agent. The confirmation id is a 43-character token. The confirmation row stores only `secret.Hash`. The idempotency response keeps the 202 body, including the plaintext id, until confirm replaces it. The id is single use, five minutes, and bound to the user, action, entry, `spec_hash`, and request hash. `POST /v1/confirmations/{confirmation_id}` takes `{"idempotency_key"}`. An invalid key is `bad_request` before lookup. The same `api_delegated` bearer may confirm. The handler checks the user, the used bit, and expiry first (`not_found`), then requires the posted key to equal the stored key (`conflict` otherwise, token unused). It re-runs the grant, relation, policy, and online checks, then returns `conflict` if the spec hash changed. Those failures do not consume the token. The token is marked used before the agent call. An agent error still consumes it and replaces the stored 202 with that error body. Console sessions skip confirmation. Logs and status never confirm and are not idempotent. The agent task uses `program_start`, `program_stop`, `program_restart`, `program_status`, or `program_logs`, with `service` null. Strings in a payload `lines` array pass through the cmdline redactor before the HTTP body and before the idempotency write. `task_reject` and a failed result of `policy_denied` both become `forbidden`.

`hello.programs` is stored on `hosts.programs` and returned on `Host`. Absent or null clears a previous policy. An object that is not the v1.3 shape is stored as disabled with an empty `run_as`. A later `services` frame does not clear it. A discovered service whose `owner` is `{kind:program, project:slug, entry:name}` is stored as `source=owned` on that project when the slug has that catalog entry. The service name and `catalog_entry` are the entry name. Otherwise the item stays `discovered` on the host's project. `systemd_unit` becomes the service name only when it matches `^[a-z0-9][a-z0-9._-]{0,62}$`. Otherwise the reported name is kept. Owned placement is the slug and entry lookup from v1.6. It does not require the host to own that project or hold a deploy share. Rediscovery may upgrade discovered to owned. It does not downgrade `declared` or owned, and it does not clear `display_name`.

Audit actions are `catalog.create`, `catalog.update` (old and new `spec_hash`), `catalog.delete`, `catalog.permissions`, `catalog.approve`, `catalog.approval_revoke`, `program.run`, `program.stop`, `program.restart`, and `program.confirmation_issued`. Delegated calls use `via=mcp`. Logs and status are not audited. A denied run, stop, or restart sets `HostID` from the parsed `host_id`, `Detail.entry` to the catalog name, and `Result` to the envelope code (`forbidden` or `unavailable`). Detail does not include env values, tokens, or the confirmation id.

`migrations/0007_catalog.sql` adds the catalog, grants, approvals, confirmations, and idempotency tables, `hosts.programs`, and `services.catalog_entry`. `deploybot_api` may select, insert, and delete those tables. UPDATE is limited to the columns a running server changes (`catalog_entries`: spec, spec_hash, command_display, updated_at; approvals: the status columns; confirmations: `used_at`; idempotency: status_code and response). `status_code` and `response` are nullable, and `idempotency_response_pair_chk` requires both null or both set. A database that already applied an earlier 0007 must have this migration re-applied before those columns can be null. Grants are replaced by delete and insert, so `catalog_grants` has no UPDATE. Postgres needs UPDATE on at least one column before `SELECT … FOR UPDATE`; entry locks use that privilege. Catalog delete is granted, so there is no `SECURITY DEFINER` helper. Soft-delete does not cascade, and `DeleteProject` deletes that project's catalog rows in both stores. `--migrate` ignores `*.down.sql`. `migrations/0007_catalog.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0007_catalog.sql'` before `--migrate` will apply 0007 again. The down script drops the new columns and tables. Running units are not stopped.

## Catalog images

Image create and replace take `{"name","kind":"image","spec":ImageSpec}`. `command_display` is the normalised reference. `spec_hash` is SHA-256 of canonical `{"env_keys","kind","spec"}`. `env_keys` is one SHA-256 per referenced set, over the sorted key names joined by newlines, not over values. An env-set `PUT` recomputes hashes for entries that reference that set and deletes their approvals inside the same transaction. `PATCH` of key visibility does not. Inline env is part of `spec`, so an inline value change does change the hash. Default image grants are admin `run,stop,restart,logs,deploy` and viewer `logs`. Program default grants are unchanged, and a program owner does not hold `deploy`. `my_actions` for an image owner is `run,stop,restart,logs,deploy,status`.

Deploy, rollback, and remove finish in the HTTP handler. `timeout_sec` is `300 + healthy_after_sec + 60` for a service deploy and for every rollback (including a job rollback), `300 + timeout_sec + 60` for a job deploy, and 60 for remove and the short actions. `Hub.Image` keeps a frame whose timeout is above 60s until that many seconds (`expires_at` is that deadline). A 60s image frame keeps the 60s TTL. Program frames stay at 15s / 60s. The handler uses `context.WithoutCancel` and then a timeout of `timeout_sec` for the hub wait on deploy, rollback, and remove. The history write, the in-flight release, and the idempotency finish use a fresh context with a five-second timeout and retry once. `http.Server` has no `WriteTimeout`. ReadHeaderTimeout is 10s, ReadTimeout is 30s, and IdleTimeout is 120s. One in-flight row per `(host, entry)` is enforced by `image_deploys_in_flight_uidx` (`WHERE in_flight`) and by the same check in the memstore. The lock is taken after the idempotency claim. A request-level failure deletes that row. A successful remove deletes it too, so remove does not appear in history. A remove that times out is HTTP 504 `timeout`, audits outcome `timeout`, and does not report `missing`. A deploy or rollback timeout with no agent payload stays HTTP 200 with outcome `timeout` and `status.state` `unknown` (`container`, `exit_code`, `started_at`, `finished_at`, and `digest` null, `restart_count` 0, `ports` empty). An agent result of `unknown` is rejected. Each in-flight row stores `in_flight_until` (the task timeout plus 120 seconds). The next deploy, rollback, or remove marks an expired row `timeout`, clears it in the same transaction, and continues. A younger row is still `conflict`. History is newest first, at most 50, and omits in-flight rows. Rollback allows the last three distinct `succeeded` or `unchanged` digests.

The secrets key is `BOT_SECRETS_KEY_FILE` (see Config). AES-256-GCM uses a fresh 12-byte nonce stored beside the ciphertext. Additional data is exactly `project_id|set|key`, `project_id|registry|host`, or `project_id|file|name`. `seal.Box` nil means the key is not configured. Encrypt and decrypt failures are logged as `encrypt failed` or `decrypt failed` with no value, nonce, ciphertext, or path. A decrypt failure on deploy or rollback does not send the task and is HTTP 500 `internal error`. The key is required before the idempotency claim when the entry references any env set, uses `secret_env`, a `files` row still names a secret file, or a stored registry host equals the parsed image host. Run, stop, restart, status, remove, and a public image with no matching registry do not need it. Logs need it only when the resolved env includes a secret key or a files row still names a secret file. A missing key is then `unavailable` `secrets key not configured`: no task is sent and no lines are returned. A plain winning value, a plain file, and a registry credential do not trigger that refusal. Inline `env` clears a secret flag. The nested task `spec` is the stored ImageSpec: inline `env` as written, and `env_sets` and `secret_env` as references. The resolved map (env sets in order, then `secret_env`, then inline `env`) is only the top-level `env`, so each secret value appears once. A top-level `files` array follows `spec.files` order when the list is non-empty, and is omitted when it is empty, as is `spec.files`. `secret_keys` (sorted, possibly `[]`) is sent on `image_deploy` and `image_rollback` only when the host's stored `programs.files` is true. It is omitted for every other host. Secret file content appears only there. `registry_auth` is that one credential, or `null`. A marshalled frame over the agent limit is `bad_request` with message `the resolved environment and files are too large for one task`. Nothing is written, the socket stays up, the in-flight row is released, and the attempt is not audited as a deploy. Every websocket write is capped at 10 seconds even when the task context is longer. The frame is not logged. `ingest.RedactPayload` still only rewrites `cmdline` and is not the secret boundary. Returned lines, error strings, audit detail, and the idempotency body replace secret env values (after precedence; inline `env` and plain env-set values are not included), the registry token, and secret file contents with `[REDACTED]` first (raw, base64, and JSON-escaped, values of at least 6 bytes), then the keyword rule. That replacement applies to free-text `lines` and to error messages. `outcome`, `digest`, `exit_code`, and every `ImageStatus` and `ImageDeploy` field are not redacted. Logs, status, run, stop, restart, and remove do that without putting the values in the task frame (`project` and `entry`, plus a `lines` count for logs). A missing key on status, run, stop, restart, and remove keeps the keyword rule and still returns the agent text. Logs do the same when the entry has no secret env key and no secret file. When it has either, a missing key refuses the call and returns no lines. A decrypt failure logs one `decrypt failed` line with no value, still returns the agent text, and redacts every secret value and secret-file piece that opened. An env or registry decrypt failure does not drop file pieces that opened. An agent field outside the outcome enum, state enum, length caps, or digest shape is outcome `failed` with the fixed message `invalid agent result` on deploy and rollback.

Env-set and registry routes use `authz.CapMembers` and require a console session. Any other session kind is `forbidden` before a decrypt. `PUT` parses dotenv before the key check, then seals every key. Inside the same transaction the store keeps each existing key's `is_secret` and stores a key new to the set as secret. A kept-plain key is written in the clear; a kept-secret key stores that fresh seal. Keys left out of the body are removed. `$` and `\` in a value are stored as written. NUL is still refused, and a value is still at most 4096 bytes. Inline ImageSpec `env` is unchanged. `DELETE` of a referenced set is `conflict` before any rehash. Registry `GET` returns host and username. Tokens are never selected into an HTTP struct. Confirmation rows store `image_digest` and `image_force` so the second step can rebuild the task. Those fields are not on the HTTP confirmation object. Issuing one still audits `program.confirmation_issued` with entry, action, and `spec_hash` only. Image run, stop, restart, logs, and status are not audited. Deploy, rollback, and remove denials are, with the reason and no values. After the agent answers, those three actions are decision `allowed`: `result` is the outcome, and `error_code` is that outcome unless it is `succeeded` or `unchanged`, which leave `error_code` null.

`hello.programs` stores `images`, `docker`, and `files` (omitted means false). Discovered `kind:"container"` may carry `container_name` and `image_digest`. An empty, oversized, or non-printable `container_name` drops that service. A missing name is kept. A name that passes is stored after the cmdline redactor. Discovery does not decrypt env sets to strip exact values. An image owner links only to an image entry; a miss keeps the reported name. `Service` JSON includes `container_name` and `image_digest` (`null` when unset). `container_name` is from migration 0001. `DeleteProject` deletes that project's env sets, registries, and project files as well as its catalog rows. Soft-delete does not cascade.

`migrations/0009_catalog_images.sql` is applied by `--migrate` as `deploybot_owner`. It widens the kind, grant, and confirmation action checks, adds `services.image_digest`, the confirmation rebuild columns, and the four new tables. `deploybot_api` receives select, insert, and delete, plus column UPDATE on the columns a running server changes. Table-level UPDATE stays false on those new tables. `--migrate` ignores `*.down.sql`. `migrations/0009_catalog_images.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0009_catalog_images.sql'` before `--migrate` will apply 0009 again.

## Project files

`GET /v1/projects/{id}/files` and `GET`, `PUT`, and `DELETE /v1/projects/{id}/files/{name}` use `authz.CapMembers` and `requireConsole`, the same gate as env sets. A delegated token is `forbidden` before a decrypt. `mcp_access` and `mcp_refresh` never reach that handler: `rejectMCPAudience` returns 401 `invalid_token` on every `/v1` route. A non-member is `not_found`. A name matches `^[a-z0-9][a-z0-9._-]{0,63}$`. Content is UTF-8, 1–65536 bytes, no NUL. A body that is not valid UTF-8 is `invalid json` before decode. `secret` omitted or JSON null means true. `sha256` is stored for every file and returned only for a plain file. List and get do not select ciphertext. `GET` of a secret file is `forbidden`. At most 64 files: the count runs inside a transaction that locks the project row. A new name past that is `bad_request` `too many files`. Replacing an existing name is allowed. `DELETE` takes that same project-row lock before the reference check. `DELETE` of a file named by an image entry of the same project is `conflict` with message `referenced by` and the sorted entry names, and writes one `file.delete` audit row (`name`, `outcome` `conflict`). The handler matches `*store.FileInUse` before the generic conflict mapping.

`seal.FileAAD` is `project_id|file|name`. A nil `Box` refuses a secret `PUT`, a deploy or rollback whose still-existing `files` rows include a secret file, and logs for that entry (`unavailable`, `secrets key not configured`). Logs return no lines and send no task. A missing file does not force the key; the task build returns `bad_request` `file <name> no longer exists` and sends nothing. Tampered ciphertext fails closed (`decrypt failed`, HTTP 500, no task).

ImageSpec rule 13 allows at most 16 rows. `file` must be a file of the same project. `target` is absolute, at most 255 bytes, with no empty, `.`, or `..` segment and no trailing slash, and it is not `/proc`, `/sys`, `/dev`, or under them. Each `file` name appears at most once. Targets are unique among file targets and must not overlap a volume target in either direction. Both sides are cleaned with `path.Clean` first. A volume target that cleans to `/` overlaps every file. Otherwise an exact match or a `/`-boundary prefix either way is `invalid files`. Volume rule 8 still accepts `/`, a trailing slash, and empty segments on an entry with no files. One file under another file's target is allowed. Errors are `invalid files` or `unknown file` and do not echo a value. Omitted or null `files` becomes `[]`. `SpecJSON` always emits `files` (empty is `[]`) for storage and for catalog GET. The hash input omits an empty list, so it matches the wave 2a canonical spec and an env-set replace does not change the hash of an entry without files. A non-empty list is part of the hash. A `GET` of an image row written before this change injects `files:[]` in the JSON response and does not rewrite the stored hash. A file `PUT` does not rehash entries.

Deploy and rollback of a non-empty `files` list require `programs.files`. The refusal is `bad_request` `this host's agent does not support files`, after the container check and before the digest check, the key check, the idempotency claim, and confirmation. `confirmImage` repeats it and does not mark the token used on denial. The task map includes `files` only when the list is non-empty. Secret-file redaction adds the whole content when it is 6–4096 bytes, each trimmed line of 16–4096 bytes, and, when the content is JSON, each string value of 16–4096 bytes and each trimmed line inside it. Those pieces are replaced with `[REDACTED]` in raw, base64, and JSON-escaped form on `image_logs` and on deploy and rollback result lines. Secret files under 6 bytes are not redacted from logs. A secret whose single line is longer than 4096 bytes is not exact-matched (the per-piece bound; helper log lines are cut at 2048 bytes). Plain file content is not redacted. A missing or undecryptable sibling is skipped while building that set. An env or registry decrypt failure does not drop pieces from files that opened. Deploy and rollback still refuse a missing file. Run, stop, restart, logs, status, and remove do not send files. Audit is `file.put` (`name`, `is_secret`, `size`) and `file.delete` (`name`, `outcome`). A completed delete has `outcome` `deleted`. A delete refused because an entry still names the file has `outcome` `conflict`. Neither row contains content or `sha256`.

`migrations/0010_project_files.sql` creates `app.project_files` (PK `(project_id, name)`, `ON DELETE CASCADE`, form check for plain versus secret, name and sha256 checks). `deploybot_api` gets select, insert, and delete, and column UPDATE on the replace columns. Table-level UPDATE stays false. The 64-file cap is not a constraint. `--migrate` ignores `0010_project_files.down.sql`. That file is a hand-run rollback: edit entries first, take a dump (it drops ciphertext), run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0010_project_files.sql'`.

## Health-check edits over MCP

A console `PUT /v1/services/{id}/health-checks` is unchanged: it replaces the set and pushes `config_update`. `idempotency_key` on that call is ignored, and the call does not claim the key. An `api_delegated` session must send a v1.6 idempotency key. The handler still checks permission, the share rules, and the body (at most 10 checks, port open on the service, protocol, path, interval, expect) before it looks at the key. A failure there is `bad_request` and claims nothing. A valid delegated call stores a plan and returns 202. The check rows stay as they were, and no `config_update` is pushed.

The plan sentence matches the v1.10 example, with the label and each HTTP path Go-quoted (`strconv.Quote`). The host name is not quoted. The label is the trimmed display name, or the discovered name when that is empty. A tcp item is `tcp <port>` with no interval. An http item is `http <port> <quoted path> every <interval> s`. A check with `enabled` false ends with ` (disabled)`. Items stay in request order. Each port that has both protocols adds ` (tcp <port> is redundant with http <port>)`, ports ascending. An empty set says `will remove all health checks from <quoted label> (<host>)`. One check uses the singular `health check`. The redundant tcp check is still stored.

The confirmation id is a catalog-style token: 256 bits, base64url, stored only as SHA-256. It expires five minutes after issue, is single-use, and is bound to the user, the service, a SHA-256 of the normalized checks in request order plus the service id, and a SHA-256 of the current check set. The current-set hash sorts a copy by protocol, port, path, interval, expect, and enabled, so a memstore map walk cannot change it. Check ids are not part of either hash. The idempotency key is not part of the request hash. The same user, key, and normalized body replays the stored 202. A different body with that key is `conflict`. Confirm requires the same key. A mismatch is `conflict` and does not consume the plan.

`POST /v1/confirmations/{id}` loads `catalog_confirmations` first. A miss loads `service_confirmations`, and a miss there loads `catalog_write_confirmations`. Unknown, used, expired, and foreign ids are `not_found`. Confirm loads the service again and runs `CapServiceWrite` with the same share rules. A missing service is `not_found`. A denial is `forbidden` and leaves the plan unused. The handler hashes the current set once. A mismatch is `conflict` with message `conflict`, and the plan stays unused. A match calls the store, which locks the service row (`SELECT … FOR UPDATE` on `app.services`; the memstore holds its mutex), re-reads the set, and marks the plan and replaces the checks in that same transaction. A set that changed after the handler's first read is `conflict`, the transaction rolls back, and the plan stays unused, so a later confirm still sees the conflict. The console replace takes the same service lock. A match pushes `config_update` and returns `{"checks":[HealthCheck]}`. The idempotency row then holds that 200, so repeating the original PUT replays it and does not replace again. A conflict does not replace that stored 202.

Audit is `health_checks.confirmation_issued` at issue (`service` label, `host` name, `count`) and `health_checks.replace` on the replace, both `via` `mcp` for a delegated session. Detail does not include the token or the check paths. The audit project is the host's owning project. The confirmation row's `project_id` is the service's project, which is what the share check uses.

`migrations/0011_service_confirmations.sql` creates `app.service_confirmations`. Columns follow v1.10 item 7, including `checks jsonb NOT NULL` (a JSON array of the normalized inputs, in request order, applied on confirm and not returned on the 202). `action` is fixed to `health_checks`. The service foreign key is `ON DELETE CASCADE`. User and project foreign keys match catalog confirmations. `deploybot_api` may select, insert, and delete, and may update only `used_at`. Table-level UPDATE stays false. `--migrate` ignores `0011_service_confirmations.down.sql`. That file is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0011_service_confirmations.sql'`. Pending plans are dropped. Nothing they named was applied yet.

## Catalog writes over MCP

An `api_delegated` session that creates, replaces, or deletes an image catalog entry validates the request and returns 202 `{confirmation_id, plan, expires_at}`. Nothing is written until `POST /v1/confirmations/{id}`. The plan names the entry and the changed fields. Inline env is shown as `KEY=value`. Entrypoint is listed when set. Restart is listed when it is not the kind's default. Env-set values, secret_env values, and file contents are omitted. The entry name, project name, image, command and entrypoint arguments, user, restart, env-set names, env keys and values, and volume and file names and targets stay bare only when they match `^[A-Za-z0-9._:/@+=-]+$`. Every other value is Go-quoted (`strconv.Quote`), so the sentence has no raw `;`, line separator, or bidi override from those fields. A program create, replace, or delete from that session is `forbidden` with message `program entries are edited in the console`. That refusal, and a delegated catalog permission change, host catalog approval, or catalog env route, is audited `decision=denied` with `via` `mcp`. Env-set denials use `env_set.list`, `env_set.get`, `env_set.replace`, `env_set.delete`, or `env_set.key_visibility`. Confirm looks up `catalog_write_confirmations` after the two earlier tables, re-checks the name or `spec_hash`, and applies the stored spec through the console write path. Applied `catalog.create`, `catalog.update`, and `catalog.delete` rows use `via` `mcp` whichever session confirms them. Issue writes `catalog.write_confirmation_issued` with the action and the entry name. A successful confirm deletes the plan row in that transaction. Storing a new plan deletes rows whose `expires_at` is already past. Project delete removes that project's rows in the same transaction, because the soft-delete does not fire the foreign key. Catalog permission changes, host catalog approvals, and catalog env routes stay console-only for a delegated session. `migrations/0013_catalog_write_confirmations.sql` creates the table. `deploybot_api` may select, insert, and delete, and may update only `used_at`. `user_id` and `project_id` both use `ON DELETE CASCADE`. `--migrate` does not apply `0013_catalog_write_confirmations.down.sql`.
