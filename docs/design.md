# bot-api-server: per-repo design

**Date:** 2026-10-13. **Status:** Approved design (D1–D31), wave 1 = phase 1. D34 (2026-10-14) amends umbrella D21. Service names and `GET /v1/projects/{id}/services` (2026-10-14) follow `docs/spec-project-services.md`. The MCP OAuth authorization server (2026-10-14) follows `docs/spec-mcp-oauth.md` and `docs/contracts/oauth-v1.md`. Project invite links (2026-10-15) follow `docs/spec-project-invites.md` and api-v1 v1.5. Project catalog programs (2026-10-15) follow `docs/spec-project-catalog.md` wave 1, api-v1 v1.6, and the v1.6.1 amendments. The v1.3.1 environment denylist is enforced here. The helper socket and unit hardening in agent-protocol v1.3.1 are not implemented in this server.
Cross-repo design: umbrella `docs/design-bot-agent-deploy.md` §2 (permissions), §3 (auth), §6 (server, app schema, Postgres roles and metrics). Contracts: `docs/contracts/`.

## Layout

```
cmd/bot-api-server/        main: config, DB pool, migrations on start (flag), HTTP server
internal/config/           env config (below)
internal/db/               pgx pool, migrations (embedded SQL), queries
internal/auth/             Google OIDC + PKCE, sessions, device flow, MCP OAuth tokens
internal/authz/            authorize(user, project, capability), plus host relation (D34)
internal/api/              REST handlers, envelope, error mapping
internal/agentws/          /agent/v1/ws: enroll, hello, heartbeat, ingest, tasks, hub of live connections
internal/ingest/           sample validation (allowlists) and batched inserts
internal/audit/            append-only audit writer
migrations/                0001_app.sql, 0002_metrics.sql (TimescaleDB hypertables), 0003_shared_hosts.sql, 0004_service_names.sql, 0005_mcp_oauth.sql, 0006_invites.sql, 0007_catalog.sql, 0008_service_gone.sql
```

## Config (env)

| Var | Purpose |
|---|---|
| `BOT_API_LISTEN` | e.g. `127.0.0.1:8090` |
| `DATABASE_URL` | Postgres `deploybot` as `deploybot_api` |
| `BOT_API_MIGRATE_DATABASE_URL` | optional; the migration login (owner). Migrations run only with `--migrate`. |
| `BOT_API_GOOGLE_CLIENT_ID`, `BOT_API_GOOGLE_CLIENT_SECRET` | OAuth client |
| `BOT_API_OAUTH_REDIRECT_URIS` | comma-separated allowlist (console callbacks) |
| `BOT_API_DEVICE_VERIFICATION_URI` | console `/device` URL |
| `BOT_API_AGENT_WS_URL` | the public `wss://…/agent/v1/ws` shown in `install_command` |
| `BOT_API_PUBLIC_ORIGIN` | OAuth issuer (trailing slash removed) and the startup log |
| `BOT_API_MCP_RESOURCE` | MCP audience. When set, startup reads the client secret file before opening the database |
| `BOT_API_CONSOLE_ORIGIN` | browser origin for `/oauth/authorize` consent redirects and for invite links (`<origin>/invite/<token>`) |
| `BOT_API_MCP_CLIENT_SECRET_FILE` | mode `0600` file; first line is the plaintext `bot-mcp-server` secret, at least 32 characters |

TLS terminates at the reverse proxy in production; dev listens on the tailnet.

## Notes

- One process. In-flight tasks, OAuth states, and live agent connections are in memory.
- Metrics tables use `timestamptz`. Raw retention is 7 days; hourly continuous aggregates are kept 1 year (add the policies in migrations; they need TimescaleDB enabled by Joe).

## D34 Shared hosts

Amends umbrella D21 ("a host belongs to exactly one project"). The host still has one owning project (`hosts.project_id`). `app.host_shares` grants another project `metrics` or `deploy` access. A row whose project is the owning project is rejected by a `BEFORE` trigger and by the store. `services.project_id` records which project a service belongs to. The agent still enrolls with no protocol change; a discovered service is inserted on the host's owning project, and rediscovery does not move `project_id`.

Permission checks for host and service routes use `authz.HostRelation` and `authz.AuthorizeHost` (spec §4). A user who is in both the owning project and a share is an owner; that clears the share list. A user in several shares keeps every share. Host view, status, and metrics are allowed when any share allows them. A service check uses only the share whose project is that service's project. `GET /v1/hosts/{id}` `share_level` is the highest of those shares (`deploy` over `metrics`). `GET /v1/projects/{id}/hosts` is different: the label is relative to that project, so the same user listing the sharing project still sees `relation: "shared"`. Owned rows come first, then shared rows, each by name in byte order (`COLLATE "C"`). The host-list cursor is `(rel_rank, name, id)`. The next page compares those values and does not look the cursor host up. A cursor in the previous `(time, id)` shape is rejected. Deploy shares still see only that project's services; anyone who can see the host gets the full process list and may snapshot (v1.1.1). A caller in two deploy shares sees both projects. Metrics shares can read the host and its charts.

Deleting a sharing project drops its shares and moves its services on other hosts back to those hosts' owners, in the same transaction. Deleting the owning project still revokes host credentials, and its shares go too. Deleting a host row drops `host_shares` by `ON DELETE CASCADE`.

`migrations/0003_shared_hosts.sql` is applied by `--migrate` (as `deploybot_owner`). It backfills `services.project_id`, then sets `NOT NULL`, and grants `deploybot_api` select, insert, update, and delete on `app.host_shares`. `--migrate` ignores `*.down.sql`. `migrations/0003_shared_hosts.down.sql` is a hand-run rollback for before phase 2: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0003_shared_hosts.sql'` before `--migrate` will apply 0003 again.

## Service names

`services.display_name` is the name a person types. `services.owner_user` is the account that owns the listening socket, copied from the agent's `Discovered.user`. Both are nullable. Rediscovery updates `owner_user` and the other discovered columns; it does not write `display_name`. A value that is empty, not printable, or longer than 64 bytes is stored as null and does not drop the service.

`PATCH /v1/services/{id}` sets or clears `display_name`. The body is that one field. The handler trims it and requires 1–64 printable characters. The edit permission is the shared-hosts service write capability: owner admin+, or a deploy-share admin for a service whose project is that share. A case-insensitive duplicate on the same host is `conflict`, from the partial unique index. The audit action is `service.rename` with detail `from` and `to`, on success and on denial.

`GET /v1/projects/{id}/services` requires project membership (`CapRead`). Rows are every service on hosts the project owns, plus services whose `project_id` is that project on hosts shared at `deploy`. A metrics share contributes nothing, including services that belong to the metrics project. Each row is the Service object plus `host_name`, `host_status` (the same rules as `Host.status`), and `project_name`. Search, sort, `total`, and paging run in SQL: one count and one page. `q` is bound with `LIKE` wildcards escaped. Sort and direction are an allowlist. Names sort by byte order of the lowercased label (`COLLATE "C"`), not locale. Host and kind use that same collation on the stored text. Ties break by `id` ascending. Nulls sort last in both directions. The cursor is opaque base64url JSON `{o, h}`: an offset and a short hash of `q`, `host_id`, `sort`, `dir`, and `view`. The first page has `prev_cursor` null. `GET /v1/hosts/{id}/services` orders by name in byte order (`COLLATE "C"`), like every other name sort, so Postgres and memstore agree. That list is otherwise unchanged apart from the two new Service fields.

`migrations/0004_service_names.sql` adds the columns and `services_host_display_name_uidx`. `services_project_idx` already exists from 0003; 0004 creates it only if it is missing, and the down script does not drop it. `--migrate` does not apply `migrations/0004_service_names.down.sql`. Running that file by hand drops the two columns and the unique index. Names typed by people are lost. Then `DELETE FROM app.schema_migrations WHERE name = '0004_service_names.sql'` before `--migrate` will apply 0004 again. Grants are unchanged.

`services.gone_at` is when a service was missing from its host's latest complete services report. Null means that report included it. Presence uses the stored name after placement, so a matching catalog entry is stored under the entry name, not the name the agent sent. The upsert and the presence update run in one transaction when the report is complete: unreported rows that are not already gone get `gone_at` set to the report time, and reported rows have `gone_at` cleared. An already-gone row keeps its time. Other hosts are not modified. A `services` frame is that full set when every element is valid. An empty array is an empty set. A mix of valid and invalid elements still upserts the valid rows and clears their `gone_at`, and does not mark any other row gone. An array whose every element is invalid, or a payload that is absent, blank, or JSON `null`, is not a report. `hello.services` follows the same rule when `services_complete` is absent or `true`. `services_complete: false` and JSON `null` write nothing. A non-bool fails the frame. `GET /v1/projects/{id}/services` accepts `view` `all` (default), `deploybot` (`owned` and `declared`), or `deploybot_and_discovered` (those plus discovered rows still present). Anything else is `bad_request`. Search, sort, paging, and `total` stay inside the view, and the cursor hash includes the view. `sort=status` keeps gone rows after present rows in both directions. Host and service reads include `gone_at` and do not filter by view. `migrations/0008_service_gone.sql` adds the nullable column and backfills each host from its own newest `last_seen_at`. `--migrate` does not apply `migrations/0008_service_gone.down.sql`. Running that file by hand drops the column. Then `DELETE FROM app.schema_migrations WHERE name = '0008_service_gone.sql'` before `--migrate` will apply 0008 again. Grants are unchanged.

## MCP OAuth authorization server

Public clients register themselves. The browser consent routes, the device-code lookup and approve/deny routes, and `GET`/`DELETE /v1/me/grants` require a console session. Any other session kind on those routes is 401. `POST /oauth/token` accepts `authorization_code`, `refresh_token`, and the token-exchange grant. Only `bot-mcp-server`, authenticated with HTTP Basic and the secret from `BOT_API_MCP_CLIENT_SECRET_FILE`, may call token exchange. A request that passes that Basic authentication is not counted against the token endpoint's 60-per-minute per-IP limit. A missing or wrong secret is counted. That client is inserted at process start from the SHA-256 of the file's first line. It is not created by dynamic registration. Codes, refresh tokens, access tokens, and the client secret are stored as SHA-256. Comparison is constant-time. Identifiers and codes are at least 128 bits from `crypto/rand`; tokens are 256 bits. A second redemption of an authorization code revokes every session in that grant family, including tokens from later refreshes and `api_delegated` sessions. Presenting an already-rotated refresh token does the same.

An `mcp_access`, `mcp_refresh`, or legacy `mcp` session on any `/v1/*` route is rejected with `invalid_token` before the handler runs. An `api_delegated` token acts as its user. Audit rows it causes use `via = 'mcp'`. The column check is `allowed|denied`, so an allow or deny decision is stored as `allowed` or `denied`.

`migrations/0005_mcp_oauth.sql` is applied by `--migrate` as `deploybot_owner`. It adds `app.oauth_clients`, `app.oauth_grants`, `app.oauth_requests`, and `app.oauth_codes`, the session columns `audience`, `grant_id`, `client_id`, `code_id`, and `rotated_at`, and widens `sessions_kind_chk` to `console|mcp|mcp_access|mcp_refresh|api_delegated`. `kind = 'mcp'` stays legal so the cut-over can expire those rows in place: `UPDATE app.sessions SET expires_at = now() WHERE kind = 'mcp' AND expires_at > now()`. `deploybot-cli` is inserted for the device flow. `deploybot_api` receives select, insert, update, and delete on the four new tables. `--migrate` ignores `*.down.sql`. `migrations/0005_mcp_oauth.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0005_mcp_oauth.sql'` before `--migrate` will apply 0005 again. The down script deletes sessions whose kind is not `console` or `mcp`, restores the 0001 kind check, and drops the new columns and tables. Legacy `mcp` rows stay expired. Clients, grants, codes, and pending requests are lost.

## Project invite links

An invite is a bearer token for project membership, separate from host join tokens. The plaintext is 256 bits, 43-character unpadded base64url, shown once in `POST /v1/projects/{id}/invites` as `token` and as `url`. The store keeps only `secret.Hash` of that string. List, revoke, lookup, and accept never return it. Logs and audit detail do not contain it or its hash.

`url` is `<BOT_API_CONSOLE_ORIGIN>/invite/<token>`. The handler trims trailing slashes on the origin, the same way the OAuth consent redirect does. An empty origin fails the create with 500 before `secret.NewToken` runs. Admin routes use `authz.CapMembers` (owner or admin). A viewer is `forbidden`. A non-member is `not_found`. Lookup and accept require a `console` session; another kind is 401 `unauthorized`. Those two routes call `authz.Authorize` with `CapSession`, then `auth.AllowInvite`: 30 per minute per user and 60 per minute per source IP, one window, and a rejected call is not counted. The HTTP body is the v1 envelope `rate_limited` (429). The OAuth token endpoint still uses its own `{"error":"rate_limited"}` body.

Lookup is a plain select. It returns the invite's role and `already_member`, and it does not write. Accept locks the invite row by `UPDATE app.invites SET uses = uses WHERE token_hash = $1`, which `deploybot_api` is allowed to do. `SELECT … FOR UPDATE` would also need `UPDATE` on every returned column, and this role only has `UPDATE` on `uses` and `revoked_at`. The lock update is rolled back unless a new membership row was inserted and `uses` was incremented. An existing member gets their current role back; `uses` and the role stay as they were. A new member is inserted with the invite's role and `added_by` set to the invite's `created_by`. `uses` is incremented only while `uses < max_uses`. The memstore holds its mutex for the whole accept, so the cap is the same there. Unknown, malformed, expired, revoked, and used-up tokens hash to a lookup and return one `not_found` body. A used-up invite is `not_found` even for someone who is already a member.

Audit rows are `invite.create` (invite id, role, max_uses, expires_at), `invite.revoke` (invite id), and `invite.accept` (invite id, user id), including an accept that finds an existing member. Lookup writes no audit row.

`migrations/0006_invites.sql` is applied by `--migrate` as `deploybot_owner`. `app.invites.project_id` references `app.projects` `ON DELETE CASCADE`. `token_hash` is unique and 32 bytes. `role` is `admin` or `viewer`. `max_uses` is 1–50. `uses` is 0–`max_uses`. Default privileges would grant `deploybot_api` full CRUD, so the migration revokes that and grants select, insert, and update of `uses` and `revoked_at` only. Soft-delete does not fire the foreign key. `DeleteProject` calls `app.invites_delete_for_project`, a `SECURITY DEFINER` function with `search_path = pg_catalog, app`, executable by `deploybot_api` and not by `PUBLIC`. The memstore deletes that project's invite rows under the same mutex. `--migrate` ignores `*.down.sql`. `migrations/0006_invites.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0006_invites.sql'` before `--migrate` will apply 0006 again. The down script drops the function and the table. Memberships already created by an accept stay. Invite links stop working.

## Project catalog (programs)

Wave 1 stores program entries only. `kind` other than `program`, and any body that contains `secret_env`, is refused with `not_implemented` (HTTP 501) before unknown-field checks. Image entries and the `docker run` parser are not implemented. The kind check on `catalog_entries` allows only `program`, so wave 2 needs a new migration.

An owner creates and replaces entries. The server splits `command` with POSIX word rules (quotes and backslash escapes only). `shell=false` refuses pipes, operators, redirects, expansion, globs, and a first word `cd`. Leading `KEY=value` words are hoisted into `env`. Keys that start with `LD_` or `DYLD_`, and `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `IFS`, `PYTHONPATH`, `PYTHONSTARTUP`, `PERL5OPT`, `PERL5LIB`, `RUBYOPT`, and `RUBYLIB`, are refused with `bad_request` and the message `this variable changes what the program runs`, including hoisted words. A `shell=true` line is not scanned for those names. `shell=true` stores `exec=/bin/sh` and `args=["-c", line]`. `spec_hash` is the lowercase hex SHA-256 of the canonical JSON `{"kind":"program","spec":{...}}` with keys sorted and no whitespace. `exec` is part of that document. `command_display` is the argv re-joined with POSIX quoting, or the raw line in shell mode.

Default grants are `role:admin` → run, stop, restart, logs, and `role:viewer` → logs. The owner always has run, stop, restart, logs, and status, and cannot be a subject. `status` is not stored; it is allowed when the caller holds any stored action. `my_actions` is that list in the order run, stop, restart, logs, status. List returns an entry only when `my_actions` is non-empty. A member with no grant who fetches one entry gets `forbidden`. A non-member gets `not_found`.

Run, stop, restart, logs, and status use one ordered chain. Membership of project `{id}` is `not_found` before the body is read. Invalid JSON and an invalid `host_id` are `bad_request`. A missing grant is then `forbidden`, including when `idempotency_key` or `lines` would also be invalid. The key format and `lines` (1..1000) are checked after the grant. The host must be owned by that project, or shared at `deploy` with an approval whose `spec_hash` is the entry's current hash and whose status is `approved`. A metrics share is `forbidden`. A deploy share without that approval is `forbidden` with the message `waiting for the host owner's approval`, and the server upserts a pending approval requested by the caller. That upsert updates a row only when it is still pending or its `spec_hash` differs. It does not clear an approved row for the current hash. The approval object includes `exec`, `args`, and `env`. Approving a hash other than the entry's current `spec_hash` returns `conflict` and writes nothing. Policy is next: null `programs`, `enabled=false`, `run_as` not listed, or shell when `allow_shell` is false. Shell also includes an exec whose base name is `sh`, `bash`, or `dash`. Each of those is `forbidden` with its own reason. The host is then required to be online. Policy denials and an offline host are not stored as idempotency responses. Run, stop, and restart then insert the idempotency row (user, key, request hash, null status, null response) before any agent call or confirmation. A second request with the same key while the response is null is `conflict` with message `request in progress`, even when the hash differs. After the outcome, including a failed dispatch, the status and body are filled in. The same request replays that body for 24 hours and does not act again. A finished row with a different hash is `conflict`. The request hash is the SHA-256 of compact JSON with keys `action`, `entry`, `host_id`, and `project_id`. It does not include `spec_hash`. An `api_delegated` session gets HTTP 202 for run, stop, and restart and does not call the agent. The confirmation id is a 43-character token. The confirmation row stores only `secret.Hash`. The idempotency response keeps the 202 body, including the plaintext id, until confirm replaces it. The id is single use, five minutes, and bound to the user, action, entry, `spec_hash`, and request hash. `POST /v1/confirmations/{confirmation_id}` takes `{"idempotency_key"}`. An invalid key is `bad_request` before lookup. The same `api_delegated` bearer may confirm. The handler checks the user, the used bit, and expiry first (`not_found`), then requires the posted key to equal the stored key (`conflict` otherwise, token unused). It re-runs the grant, relation, policy, and online checks, then returns `conflict` if the spec hash changed. Those failures do not consume the token. The token is marked used before the agent call. An agent error still consumes it and replaces the stored 202 with that error body. Console sessions skip confirmation. Logs and status never confirm and are not idempotent. The agent task uses `program_start`, `program_stop`, `program_restart`, `program_status`, or `program_logs`, with `service` null. Strings in a payload `lines` array pass through the cmdline redactor before the HTTP body and before the idempotency write. `task_reject` and a failed result of `policy_denied` both become `forbidden`.

`hello.programs` is stored on `hosts.programs` and returned on `Host`. Absent or null clears a previous policy. An object that is not the v1.3 shape is stored as disabled with an empty `run_as`. A later `services` frame does not clear it. A discovered service whose `owner` is `{kind:program, project:slug, entry:name}` is stored as `source=owned` on that project when the slug has that catalog entry. The service name and `catalog_entry` are the entry name. Otherwise the item stays `discovered` on the host's project. `systemd_unit` becomes the service name only when it matches `^[a-z0-9][a-z0-9._-]{0,62}$`. Otherwise the reported name is kept. Owned placement is the slug and entry lookup from v1.6. It does not require the host to own that project or hold a deploy share. Rediscovery may upgrade discovered to owned. It does not downgrade `declared` or owned, and it does not clear `display_name`.

Audit actions are `catalog.create`, `catalog.update` (old and new `spec_hash`), `catalog.delete`, `catalog.permissions`, `catalog.approve`, `catalog.approval_revoke`, `program.run`, `program.stop`, `program.restart`, and `program.confirmation_issued`. Delegated calls use `via=mcp`. Logs and status are not audited. A denied run, stop, or restart sets `HostID` from the parsed `host_id`, `Detail.entry` to the catalog name, and `Result` to the envelope code (`forbidden` or `unavailable`). Detail does not include env values, tokens, or the confirmation id.

`migrations/0007_catalog.sql` adds the catalog, grants, approvals, confirmations, and idempotency tables, `hosts.programs`, and `services.catalog_entry`. `deploybot_api` may select, insert, and delete those tables. UPDATE is limited to the columns a running server changes (`catalog_entries`: spec, spec_hash, command_display, updated_at; approvals: the status columns; confirmations: `used_at`; idempotency: status_code and response). `status_code` and `response` are nullable, and `idempotency_response_pair_chk` requires both null or both set. A database that already applied an earlier 0007 must have this migration re-applied before those columns can be null. Grants are replaced by delete and insert, so `catalog_grants` has no UPDATE. Postgres needs UPDATE on at least one column before `SELECT … FOR UPDATE`; entry locks use that privilege. Catalog delete is granted, so there is no `SECURITY DEFINER` helper. Soft-delete does not cascade, and `DeleteProject` deletes that project's catalog rows in both stores. `--migrate` ignores `*.down.sql`. `migrations/0007_catalog.down.sql` is a hand-run rollback: run it as `deploybot_owner`, then `DELETE FROM app.schema_migrations WHERE name = '0007_catalog.sql'` before `--migrate` will apply 0007 again. The down script drops the new columns and tables. Running units are not stopped.
